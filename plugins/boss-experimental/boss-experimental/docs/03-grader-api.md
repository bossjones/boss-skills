# The Grader API

Graders are the deterministic half of skillgrade's scoring model (the other half is
`llm_rubric`, which sends output to an LLM instead of a script). Every grader shipped or
generated by this plugin is a small, dependency-free Node script.

## The contract

A grader is a Node (CommonJS) script that:

1. **Is invoked as `node graders/<name>.js [args...] <output-file>`** — the output file path is
   always the *last* positional argument.
2. **Prints exactly one line of JSON to stdout**: `{"score": <0.0-1.0>, "details": "<string>"}`.
3. **Always exits `0`**, regardless of the score it computed — a failing check is communicated
   through `score: 0.0` in the JSON, never through a non-zero process exit code.
4. **Handles the missing-output-file case explicitly** — if the file the grader is supposed to
   inspect doesn't exist, it reports `{"score": 0.0, "details": "Output file not found: ..."}`
   rather than throwing.
5. **Requires no `chmod +x`** — every invocation goes through `node graders/script.js ...`, so
   the execute bit is never needed. (`scaffold-skill-eval`'s Constraints section states this
   explicitly: "Do NOT require `chmod +x`.")
6. **Has zero external dependencies** — only Node's `fs` and `path` builtins. This is what makes
   the graders portable across the local engine (Claude Code's `Bash` tool) and the CI engine
   (skillgrade's Docker/local providers) without an install step.

Minimal shape (from [`check-no-fails.js`](../skills/scaffold-skill-eval/references/graders/check-no-fails.js)):

```js
const fs = require("fs");
const outputFile = process.argv[2] || "output.md";

if (!fs.existsSync(outputFile)) {
    console.log(JSON.stringify({ score: 0.0, details: `Output file not found: ${outputFile}` }));
    process.exit(0);
}

const content = fs.readFileSync(outputFile, "utf-8");
const failCount = (content.match(/\| FAIL/gi) || []).length;

if (failCount === 0) {
    console.log(JSON.stringify({ score: 1.0, details: "No FAIL statuses found — valid project passed all checks" }));
} else {
    console.log(JSON.stringify({ score: 0.0, details: `Found ${failCount} unexpected FAIL statuses` }));
}
```

## How a grader plugs into `eval.yaml`

A `deterministic` grader entry supplies the exact shell command in `run`:

```yaml
graders:
  - type: deterministic
    run: node graders/check-fail-present.js "Config exists" output.md
    weight: 1.0
```

The command runs from the `eval/` directory. In the CI engine, `output.md` is whatever file the
task's `instruction` told the agent to write. In the local engine (`/run-skill-eval`), Claude
Code substitutes the literal `output.md` in the command for the real per-task filename
`output-{task-name}.md` before executing it with `Bash` — this substitution is spelled out in
`run-skill-eval`'s `SKILL.md` step 3(d).

## The shipped reusable graders

All eight live under
[`skills/scaffold-skill-eval/references/graders/`](../skills/scaffold-skill-eval/references/graders/).
`scaffold-skill-eval`'s own `SKILL.md` tells the scaffolder to prefer these over writing new ones.

| Grader | Usage | Scores 1.0 when… |
|---|---|---|
| `check-fail-present.js` | `node check-fail-present.js <pattern> <output-file>` | A `FAIL` status appears next to `<pattern>` (regex, case-insensitive, either order) |
| `check-no-fails.js` | `node check-no-fails.js <output-file>` | Zero `\| FAIL` table cells appear anywhere — for positive controls |
| `check-warn-or-fail-present.js` | `node check-warn-or-fail-present.js <pattern> <output-file>` | Either `WARN` or `FAIL` appears next to `<pattern>` |
| `check-no-fail-for-pattern.js` | `node check-no-fail-for-pattern.js <pattern> <output-file>` | No `FAIL` appears next to `<pattern>` (inverse of `check-fail-present.js` — used for "this should NOT fail" assertions, e.g. the `custom-pipeline-agent` fixture) |
| `check-eval-structure.js` | `node check-eval-structure.js <eval-dir>` | `eval.yaml`, `run_eval.sh`, `README.md` all exist, at least one `graders/*.js` exists, at least one `test-fixtures/` subdirectory exists |
| `check-eval-yaml-tasks.js` | `node check-eval-yaml-tasks.js <min-tasks> <eval-dir>` | `eval.yaml` has `version: "1"`, a `defaults:` block, at least `<min-tasks>` `- name:` entries, and every task section has both `graders:` and `instruction:` |
| `check-fixture-count.js` | `node check-fixture-count.js <min-count> <eval-dir>` | `test-fixtures/` contains at least `<min-count>` subdirectories |
| `check-stopped-early.js` | `node check-stopped-early.js <eval-dir> <output-file>` | `eval.yaml` was **not** created (correct behavior for an invalid target) **and** the output mentions the problem (`stop`/`missing`/`error`/`not found`/`no skill|description|frontmatter`) — scores `0.5` if no `eval.yaml` was created but no clear error text is found either |

The first four (`check-fail-present.js`, `check-no-fails.js`, `check-warn-or-fail-present.js`,
`check-no-fail-for-pattern.js`) are also vendored **byte-identical** into
[`skills/claude-config-validation/eval/graders/`](../skills/claude-config-validation/eval/graders/)
— that skill's `eval.yaml` uses exactly these four, referencing named checks like `"Canonical
agents"`, `"CLAUDE.md size"`, or `"context discipline"` as the `<pattern>` argument. The last
four graders (`check-eval-structure.js`, `check-eval-yaml-tasks.js`, `check-fixture-count.js`,
`check-stopped-early.js`) exist to grade `scaffold-skill-eval` *itself* — they inspect an
`eval/` directory's structure/`eval.yaml`, not a skill's PASS/WARN/FAIL output — and aren't
needed by skills that only consume the pattern-matching graders.

## Writing a new grader

Follow `scaffold-skill-eval`'s guidance (step 4 of its procedure):

1. **Check whether a reusable grader already fits.** Most skills that produce a PASS/WARN/FAIL
   table only need the four pattern-matching graders above with a different `<pattern>` string.
2. **Match the target skill's actual output format.** If a skill's output is JSON, a checklist,
   or prose rather than a status table, write a grader for that shape — the scoring *protocol*
   (`{"score", "details"}` JSON) never changes, only what the script parses.
3. **Keep it zero-dependency and defensive**: `fs.existsSync` before reading, print exactly one
   JSON line, `process.exit(0)` on every path (including the early-return "file not found" path).
4. **Decide if you also need an `llm_rubric` grader.** Prefer deterministic-only when detection
   alone answers the question (did the right status appear for the right check?). Add
   `llm_rubric` as a *weighted complement* — never a replacement — when: (a) a positive control
   needs format-completeness checking a regex can't express, (b) the skill's value is in
   *recommendation quality*, not just detection (a deterministic grader only proves a WARN
   fired; an `llm_rubric` grader can judge whether the WARN's suggested fix actually names a
   file), or (c) the output is genuinely subjective prose. Don't add `llm_rubric` to every task —
   it adds cost and non-determinism.
5. **Test it against a mock output file** before wiring it into `eval.yaml` — `node
   graders/check-*.js path/to/mock-output.md` should print valid JSON.

## The `llm_rubric` grader type (non-Node)

`llm_rubric` graders have no script — the `rubric` field is prose text (or a path to one), and
the grading agent (skillgrade's LLM in CI, or Claude Code itself locally) reads the output file
and the rubric and returns the same `{"score", "details"}` shape by judgment rather than by
regex. The `rule-doc-in-routing-table` task in `claude-config-validation`'s `eval.yaml` is a
worked example — a rubric with a compound pass condition ("(1) WARN on Check 23 for X, AND (2)
do NOT flag Check 15 for the same doc") that a regex-based deterministic grader couldn't express
cleanly. In `run-skill-eval`'s local engine, the instruction to graders is explicit: *"be strict
— only score 1.0 if the output clearly meets the rubric criteria."*
