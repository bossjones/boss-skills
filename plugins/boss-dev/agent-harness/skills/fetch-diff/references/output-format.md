# Output Format

The script emits a single block of annotated unified-diff text to stdout. This
document describes the schema a caller can rely on when parsing that output —
especially when feeding line numbers into the `add-review-comment` skill.

## Overall schema

The output is the PR's unified diff, reorganized into per-file sections. Each
file section begins with the standard `diff --git a/<old> b/<new>` header, may
carry git metadata lines (`index`, `--- `, `+++ `, mode/rename lines), and then
either annotated hunk content or a single mask message.

A blank line is inserted before each `diff --git` header (except the first), so
file sections are visually separated.

Two streams matter:

- **stdout** — the annotated diff (the payload).
- **stderr** — diagnostics *and* errors. On success the only note is a
  "Detected stacked PR, fetching incremental diff" message when the PR body uses
  the stacked-PR convention (see below). Failures (missing token, invalid PR URL,
  a bad `--base` ref, or passing neither/both sources) also write to stderr and
  always pair with a **non-zero exit code**.

**Check the exit status, not just stdout.** A caller that treats stderr as purely
informational will silently swallow a fatal auth failure and see an empty diff —
which is indistinguishable from a PR that changed nothing.

## Line annotation

Inside a hunk, every content line is rewritten to a fixed-width prefix followed
by `| ` and then the original diff line (marker character included):

```text
old_line new_line | <marker> content
```

The two leading columns are right-aligned 5-wide integers. One of them is blank
depending on the change type:

| Marker (in `content`) | Columns shown        | Meaning  | How to anchor a comment        |
| --------------------- | -------------------- | -------- | ------------------------------ |
| `-`                   | old_line only        | removed  | `side=LEFT`, `line=old_line`   |
| `+`                   | new_line only        | added    | `side=RIGHT`, `line=new_line`  |
| none (leading space)  | both old and new     | context  | `side=RIGHT`, `line=new_line`  |

The hunk header `@@ -a,b +c,d @@` seeds the counters: `old_line` starts at `a`,
`new_line` at `c`. Removed lines advance only `old_line`; added lines advance
only `new_line`; context lines advance both. This mirrors how GitHub's review
API counts lines, which is why the columns map directly onto `side`/`line`.

Worked example:

```text
@@ -10,7 +10,7 @@
   10    10 |  import os
   11    11 |  import sys
   12    12 |  from typing import Optional
   13       | -from old_module import OldClass
         14 | +from new_module import NewClass
   14    15 |
   15    16 |  def process_data(input_file: str) -> dict:
```

To comment on the removed `OldClass` import: `side=LEFT`, `line=13`. To comment
on the added `NewClass` import: `side=RIGHT`, `line=14`.

## Masked files

To keep review focused on hand-written changes, some files are shown with their
headers preserved but their hunk content replaced by a one-line mask message.

**Auto-generated files** are masked with `[Auto-generated file - diff masked]`.
A file counts as auto-generated when any of the following holds:

- **It is a lock file.** One of `uv.lock`, `yarn.lock`, `package-lock.json`,
  `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`, `Cargo.lock`, `go.sum`,
  `poetry.lock`, `composer.lock`, or `Gemfile.lock`.
- **It is a minified bundle or a sourcemap.** Its name ends in `.min.js`,
  `.min.css`, or `.map`.
- **Its first line carries a generated-code marker.** Either `@generated` or
  `Generated by the protocol buffer compiler`, in a file of *any* type — not just
  `.java`. This check reads the file from the local working tree, so it only
  fires when the file exists on disk where the script runs; outside a checkout it
  is silently skipped.

```text
diff --git a/uv.lock b/uv.lock
index abc123..def456 100644
--- a/uv.lock
+++ b/uv.lock
[Auto-generated file - diff masked]
```

The mask message is emitted once per file (at the first hunk), not once per
hunk. Git metadata lines (`index`, mode changes, rename info) and the `--- ` /
`+++ ` file headers pass through; only the `+`/`-`/context body is suppressed.

### Migrations are never masked

Any path with a `migrations` directory component is **exempt** from every rule
above — including the `@generated` marker. An Alembic or Django migration
scaffolded by a tool and stamped `@generated` still arrives with full hunks.

This exemption is deliberate: a bad migration is one of the few changes that can
destroy production data, so it must always reach a reviewer. Do not treat a
migration's presence in the output as a masking bug.

## Deleted files

Deleted files are masked with `[Deleted file - diff masked]`. The deletion is
detected from the **`deleted file mode` line** — that line, and only that line, is
what triggers the mask.

Note that git repeats the real path on both sides of the `diff --git` header even
for a deletion; `/dev/null` appears only on the `+++ ` line. This matters: the
path used for `--files` glob matching is taken from the **`b/` side of the
`diff --git` header**, so `--files '*.py'` *does* match a deleted `.py` file.

```text
diff --git a/path/to/removed.py b/path/to/removed.py
deleted file mode 100644
index abc123..0000000
--- a/path/to/removed.py
+++ /dev/null
[Deleted file - diff masked]
```

Because the body is suppressed, you cannot anchor a comment to a line inside a
deleted file from this output — there is no per-line annotation to reference.

## Stacked PRs

If the PR body contains a `## Stacked PR` section (an mlflow-flavored
convention) and the current branch is the bold entry in that section, the
script fetches the *incremental* compare diff between the stacked base SHA and
the head SHA instead of the full PR diff. It announces this on stderr. In repos
that do not use stacked PRs the marker is absent and you always get the full PR
diff — no special handling is needed.
